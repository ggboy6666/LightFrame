## 采样路径与开销口径

新安装默认帧读取 500ms、硬件 2000ms、温度 5000ms，GPU 系统工作追踪关闭，默认悬浮窗为 FPS、系统 CPU、GPU 和 CPU 温度四项。升级保留已有手填间隔与指标选择；验证前应确认实际设置，必要时应用新版低开销预设。可访问的直接 GPU 节点继续读取，受限节点的缺失不会补成数值。

帧周期按实际 SurfaceFlinger 刷新周期优先、活动显示刷新率次之计算，按每轮约 100 帧为 127 条系统环缓冲留余量。例如 240Hz 时，正常读取周期上限约 416ms；这不会把实测 FPS 限制到刷新率。预算未知时不假定 60Hz。慢请求后增加等待，不积压或补跑采样；读取太慢导致的真实缓冲缺口仍保留，不能承诺在任意阻塞下捕获全部帧。

这里的自适应依据是刷新周期、缓冲容量与实际采样耗时，不是已经识别游戏 GPU 负载突增。短时系统压力仍可能发生在一次请求之内。前台任务成功读取有 1 秒缓存，失败后 5 秒重试，没有每轮启动前台查询 shell。选中且有效的图层直接读取；失效才进入有界候选查找。

采样 HandlerThread、独立采集器事务、Root 采集循环与 dump 读取线程采用后台优先级。后台线程可以降低应用争抢 CPU 的优先程度，但不会消除系统处理 RPC 的成本。Android 16 的 `--latency` 路由至 SurfaceFlinger 的 `argsMainThreadDumper`，所以帧查询仍会占用合成主线程；一次超时并不意味着系统已撤销那个请求。[官方 SurfaceFlinger 实现](https://android.googlesource.com/platform/frameworks/native/+/android16-release/services/surfaceflinger/SurfaceFlinger.cpp)

悬浮窗数值文本在采样线程缓存，常规更新每秒一次，绘制时不重新解析 JSON；隐藏后仍采样，必须显式停止才能结束采集。主页离开后停止其定时刷新。Lite 跳过记录存储和统计，但仍有帧查询、硬件读取和悬浮窗合成成本。

新记录中的计时字段按以下口径读取：

| 字段 | 含义 |
| --- | --- |
| `cycleCostMs` | 当前采集请求从准备至 backend 响应返回的耗时；不包含随后记录追加、文本格式化或界面绘制 |
| `previousCycleCostMs` | 上一轮采样线程已完成的总耗时，包括请求、记录处理、数据序列化及该轮文本缓存；不含两轮之间的等待与主线程异步绘制 |
| `previousRecordWriteCostMs` | 上一轮完整 `SessionRecorder.append` 的耗时，包括实时帧状态、CSV 格式化、写入以及该轮实际发生的文件 flush；不是单独的磁盘耗时 |
| `previousCycleSampleNs` | 上述上一轮计时对应的 tick 起点，使用单调时钟；不是当前采样的时刻 |

上一轮计时在下一条采样中保存，首次采样与暂停后恢复为空；Lite 的记录处理耗时为空。这样可以计入上一轮样本行自身的实际写入，不回写已完成的 CSV、不为计时新增立即 flush。停止前最后一轮没有下一条采样，因此这些字段不能当作完整记录的无遗漏逐轮计时。

记录统计在原始文件关闭且采集器释放之后计算。实时路径只维护必要的 FPS 和原始数据。应用及助手的 CPU / RSS 不包含系统服务处理、GPU 合成和其他并行任务的完整增量成本；平均 CPU 很低也不能证明瞬时无卡顿。

逐帧 CSV 改为重用 `StringBuilder` 与字符缓冲，保留原有十列表示、排序、去重和帧预算字段。专属回归覆盖数值和字符串等价、逗号 / 引号 / 换行处理、长行扩容、写入失败传播、错开刷新、延迟批次与完整行快照；既有帧窗口、分段和统计回归仍通过。桌面分配测量中，原来的对象数组 / 通用 CSV 编码路径约为 1583 字节每帧，新路径约 319 字节每帧，减少约 80%；这是指定桌面写入路径的分配结果，不能当作 Android 整机开销或游戏性能改善率。

样本和逐帧文件各按约 2 秒安排周期刷新，起始时间错开，常规追加每轮最多周期刷新一份脏文件；慢采样后两份都到期时也不在同一轮追赶刷新。缓冲满时仍会发生写出，暂停与停止则完整刷新，因此它不是保证每轮只发生一次磁盘写入。活动记录快照仅索引当时已写出的完整行，可能暂时少于内存中的最新采样。`previousCycleSampleNs` 已写入 CSV 并排除在普通数值指标统计之外；带前轮时刻字段的 CSV 文件回归通过，测试未回写原始文件。

## 后续验证

软件功能版本已发布，以下结果会在实际取得后追加，不将待测项目写成已通过。

1. 用户实际报告卡顿的高负载游戏同场景对比：软件停止、Full 采集且 GPU 工作追踪关闭 / HUD 可见、仅隐藏 HUD、最后关闭 FPS。FPS 与采样间隔在重新开始后生效，阶段间必须明确停止、设置并重新开始，不能以按钮状态推定已影响当前采样。
2. 每阶段约 20 秒，读取累计系统 / 进程 CPU 的端点差及结束后每个已识别监控进程的一次 PSS，保留权限限制和缺失。项目外脚本未执行设备采集；不启动额外连续 Perfetto、录屏或高频后台探测，不调整频率、温控和开发者性能设置。SurfaceFlinger 统计默认不读，确有需要时只 dump 已有统计，不启用或清空。
3. 记录操作员观察到的顿挫，并检查真实 `previousCycleCostMs`、记录处理耗时、刷新预算、有效帧窗口与采集缺口。CPU 和可选 SurfaceFlinger 统计是辅助证据；不同场景、热状态、FPS 上限或负载状态的数据不能直接解释为轻帧造成的差异。
4. 相同开关与场景下复测正式 Lite 的游戏指标、暂停和息屏恢复，并继续检查停止后的采样 / 自身 GPU 追踪清理。私有文件隔离目前以源码和字节码为依据，内部文件状态未经本机枚举，不作更强声明。
5. 继续验证 Full 从同签名旧版本在线检测、下载校验到系统安装的完整流程。Lite 的旧版在线升级及两版正式 1.0.0 的最新检测已完成；测试探针不作为正式发布资产，系统安装确认仍由 Android 管理。

目前已验证功能和开销控制策略，尚未取得最终包的高负载同场景对比结果。之前 0.2.6 菜单 / 排位界面的 GPU 与 CPU 验证保留在 [0.2.6 验证记录](VALIDATION-0.2.6.md)，不能代替本页的实际战斗压力测试，也不能证明全部卡顿原因已排除。
