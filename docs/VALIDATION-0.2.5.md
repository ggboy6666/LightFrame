# LightFrame 0.2.5 无 Root GPU 工作数据与历史界面清理

后续更正：0.2.6 检查长记录发现，此版误把 Perfetto 时钟编号 4（MONOTONIC_COARSE）当作 RAW；RAW 应为 5。下文描述的是当时实现意图及观察，GPU 精确数值与完整性结论不能当作修复后的验证。长记录另出现缓冲丢失；更正和新验证见 [0.2.6 验证记录](VALIDATION-0.2.6.md)。

日期：2026-10-02。连接用户的 vivo PA2573 / Android 16，用户确认未 Root，并允许在已打开的游戏中做短时验证。用户随后说明已使用液冷，可以研究超频；本次保持系统频率、电压、温控和性能模式设置，没有进行超频。

## GPU 来源与有效性

原有 GED、gpufreq、Mali 与 devfreq 只读使用率 / 频率节点依然拒绝访问或不存在。Shell UID 2000 可以通过 Perfetto 取得 `power/gpu_work_period` 和 `power/gpu_frequency`；0.2.5 在节点不可用且未指定自定义节点时接入这个通道。

- 工作忙碌率：同一 GPU 已报告的完整工作区间取并集，占完整 1 秒窗口的百分比。跨 UID 重叠和重复区间只计一次。`active_duration == end-start` 才能确定整个区间都在工作；部分活跃区间的位置不明时不猜测负载。保护内容可能未报告，因此不保证包含全部 GPU 工作，也不等于着色器核心利用率。
- 频率：最新已报告频率事件的 kHz 转 MHz，保存事件时间和年龄。没有有效事件不推测当前频率。完整追踪只有频率、没有可用忙碌区间时，独立保留频率，负载继续为空。
- 时钟：GPU 工作区间的 MONOTONIC_RAW 经 ClockSnapshot 转成 MONOTONIC；ftrace BOOTTIME 频率事件也转换。不能混用包含设备休眠时间的 BOOTTIME 与应用呈现时钟。捕获中映射变化超过 1ms 时拒绝结果。
- 完成证据：CLI 正常结束后读取文件，还须有成功最终 flush、完整 START / END ftrace 统计和 read-tracing-buffers-completed。中央 / 内核缓冲丢失、解析错误、时钟缺失、未结束或截断时不发布任一数值。
- 统计窗口：为覆盖跨窗周期和驱动延迟，窗口结束早于捕获截止至少 3.1 秒。没有完整工作事件不能把缺失当成零；在已经证明工作事件可用的完整空窗口中，真实零仍可保存。

时钟与工作周期上限参考 [Android 16 GPU work BPF 源码](https://android.googlesource.com/platform/frameworks/native/+/android16-release/services/gpuservice/gpuwork/bpfprogs/gpuWork.c)。TraceStats、ftrace 和时钟协议按 [Perfetto v49 官方协议](https://github.com/google/perfetto/tree/v49.0/protos/perfetto/trace)读取。实现是有边界的纯 Java 读取器，没有打包外部分析器、厂商库或研究用原生计数器。

## 采集与界面

每次追踪约 8 秒，只开启上述两个事件，512KiB DISCARD 缓冲；输出文件上限 4MiB，CLI 输出上限 128KiB，进程最长 18 秒，失败退避 30 秒。独立线程捕获和解析，主采样读取已发布快照；首次显示“采样中”。暂停、息屏、正常停止和采集器关闭取消自己创建的子进程，仅删除本次随机命名的配置 / 追踪文件。

硬件间隔仍由用户填写。更小间隔不会提高这个 GPU 通道的约 8 秒返回速度；较长间隔会更少读取，并允许保留带真实年龄的最近结果。此通道并非连续覆盖每一秒。CSV 保存口径、窗口起止、频率事件时间和每行数据年龄；这些状态 / 时间字段不参加硬件指标统计。实时页及历史明细解释来源与延迟，曲线仍按记录行时间显示，不能把异步值当作该行时刻的瞬时负载。

历史总览、没有采样的记录页、没有逐帧数据的逐帧页移除无作用的时间浏览控件；有数据的曲线、采样和逐帧页保留准确时刻、区间、拖动、缩放及原始值查看。

## 短时实机观察

先关闭 GPU 工作通道，再开启，使用已安装 APK 的实际采集代码、Shell UID 2000，游戏包为 `com.tencent.jkchess`。本次没有以相同场景回放做受控测试。

| 观察项 | 不启用 GPU 工作通道 | 启用 GPU 工作通道 |
| --- | ---: | ---: |
| 观察时长 | 12.20s | 20.04s |
| 捕获帧数 | 1,421 | 2,420 |
| 有效滚动 FPS 样本平均 | 112.21 | 114.72 |
| 捕获帧间隔中位数 | 8.332ms | 8.332ms |
| 捕获帧间隔最大值 | 41.660ms | 25.010ms |
| >33.4ms / >100ms 间隔 | 1 / 0 | 0 / 0 |
| 采集进程 CPU（单核当量） | 1.74% | 3.37% |
| 单次请求平均（排除首次） | 13.23ms | 16.94ms |
| GPU 工作忙碌率 | 未请求 | 87.5181%、88.5659% |

FPS 一行是滚动样本的平均，不是帧数除以时长。CPU 一行只包含测试采集进程，未包含悬浮窗、完整应用、Perfetto 子进程或系统服务。时长、场景和首次初始化不同，这些数字不能证明采集提升 FPS、没有额外负担或长期高负载不卡。用户此前报告卡顿，停止诊断后未发现遗留追踪或采集进程，但没有确定原卡顿原因，不能声称已经治愈所有游戏卡顿。

另一次实际采集返回工作忙碌率 83.3333%、84.8468%，频率事件为 962 / 1430MHz。该次用户更换游戏、固定目标与前台不一致，帧源为空，不作为 FPS 对比证据。

最终 Windows APK 为 172,811 字节，SHA-256 `9d05e48bd6ce6b53a5d1fa39241579baa5f912e1f28c0bdea7da2138946416ac`；ZIP CRC、4 字节对齐和 v2 / v3 签名通过。安装命令等待超过 30 秒，但后续设备读取的已安装 APK 摘要与最终本机文件完全一致，包版本码为 7，没有重复卸载或清除数据。

Shizuku 原服务未运行，通过已安装应用的官方 ADB 启动器恢复 Shell 服务，轻帧保留已有授权。随后直接在轻帧开始 / 停止并保存一条约 120.55 秒、466 行的验证记录。该次前台为轻帧界面，FPS 缺失是预期行为；它是软件内 GPU 和保存流程检查，不是游戏帧率测量。实际悬浮窗显示 GPU 负载约 3.0%、频率 26MHz，实时页显示工作忙碌率口径与动态年龄，历史总览均值与之对应。

总览页实际没有时间浏览控件；GPU 曲线页有时间浏览、准确时刻、区间、放大 / 缩小等控件，并成功加载这条记录。此前旧记录仍在列表中。该次总览显示应用与采集器 CPU 均值约 9.9% 单核当量、RSS 378MB；UI 自动化与前台绘制影响此数值，RSS 含共享页，不能解释为后台游戏的独占开销，更不能用前述采集进程 3.37% 替代完整应用开销。PSS、长期游戏功耗及内存增量未测。

保存后 MonitorService 已结束，Perfetto 活动追踪为 0，返回原游戏前台。授权管理服务继续可用，没有留下性能录制。
